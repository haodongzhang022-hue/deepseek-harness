# 自动化门管道由：可插拔适配器的通用管道监控

日期：2026-08-24
状态：proposed —— Phase A 实施目标

## 背景

omni-meta 量化金融项目已有一套在跑的发布管道：8009-8016 测试 agent 以 8066 为基线迭代，变更提交进 8008 整合队列，整合方测试后带证据批准或驳回，通过项进入 8027 部署验证再到 8028/8066 晋升。今天每一步都靠手动调用 MCP 工具触发，没有任何东西监听队列；被驳回的工作就此搁浅——没有机制把驳回路由回源 agent 会话。

本 harness 同时有通用的 automation-calendar 视图。用户方向明确：监控/路由层作为**通用能力**建在本仓库，借鉴金融管道形态但不耦合。另一条工作线会把金融 release-control 服务抽象成通用插件；本路由器必须同时适配两者而不返工。

## 决策

四层一个接缝：

1. **门契约（通用，落在本仓库）。** 覆盖任意门管道的窄适配接口：
   - `listItems(state?)) —— 队列/测试中/驳回/批准条目快照
   - `itemIdentity(item)` → 稳定 id + 源端口 + 目标会话线索
   - `recordResult(...)`、`claim(...)` —— 命令半边，按适配器能力声明
   适配器实现：(a) 金融 release-control，经其官方 stdio MCP 服务（`python -m release_control.mcp_server`）由本仓库 mcp-client 包驱动——不做 REST 逆向；(b) 为未来通用插件预留槽位。

2. **路由引擎（通用）。** 定时轮询适配器，diff 快照成事件（submitted/rejected/approved），每条目一行持久化状态（queued→testing→passed|rejected→notified→reiterating→resubmitted），并派发动作。状态机表是数据而非代码分支——新管道只加行。

3. **唤醒通道（dsh 原生）。** 驳回唤醒 = SDK `prompt({ sessionId, contentBlocks })`——服务端定位保留的 agent 并调 `followup(createUserMessage(...))`。消息携带驳回原因+证据+原始目标，同一个会话带着完整上下文继续迭代。投递前查注册表心跳（session_id+TTL）决定直发还是先重启。

4. **watcher 是同一引擎的消费者**（Phase B）：8008/8027/8028 变成配置条目——到货且有空闲容量就 claim、测完 record、然后挂起等下一条。Phase C intake 把新需求按能力匹配映射到端口/会话。

## 放弃了什么

- **逆向金融 REST API**：MCP stdio 面是服务官方契约且已版本化；HTTP 扒取会在对方升级时静默断裂。
- **引擎里写死端口号**：端口是适配器配置；引擎只见身份与能力。这正是未来通用插件可以即插即用的原因。
- **驳回即新开会话**：唤醒必须复用原会话——上下文连续正是目的，新会话等于重读世界。

## 后果

- 金融管道获得无人值守的夜间迭代；人只在 `record_production_decision` 本来就要求的位置介入。
- 通用插件落地后，接入一条管道 = 一个适配器文件 + 状态表若干行，引擎零改动。
- 投递风险：心跳与 prompt 之间会话死亡时，路由器退避重试并标记 notify-failed 交人工路由，不丢弃条目。

## 验证

- Phase A 验收：向 8008 注入一条驳回态条目；运行中的路由器在一个轮询周期内向注册的源会话送达 followup；条目状态流转留痕；跨重启抑制重复投递。
- 契约测试跑在假适配器上；金融适配器挂特性开关做薄冒烟。
